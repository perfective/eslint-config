= Roadmap

These findings come from repository exploration on 2026-11-15.
They are proposals for separate work, not additional instructions or authorization to change package behavior.
Recheck the referenced files before acting and remove resolved items.

== Package metadata

`package.json` declares `eslint-plugin-rxjs-x` as a peer and development dependency,
but `peerDependenciesMeta` marks the old `eslint-plugin-rxjs` name as optional.
The public sub-path remains `rxjs`, and its plugin namespace is `rxjs-x`.
The maintainer requested that the metadata mismatch be recorded for a separate fix.

Proposed follow-up: align the optional peer key in the manifest and lockfile,
then inspect the generated `dist/package.json`.
Consider a focused packaging check that optional peer metadata keys exist in `peerDependencies`
and that every declared sub-path points to generated JavaScript and declaration files.
The existing rule audit checks rules and their docs, not these packaging relationships.

== Import resolver

`eslint-plugin-import-x` replaced `eslint-plugin-import` (issue #48),
but `eslint-import-resolver-typescript` stays on v3.10.1
and `src/config/import/import-config.ts` uses the legacy `import-x/resolver` setting.
The maintainer requested a separate pull request for the resolver update, if possible.

Proposed follow-up: upgrade `eslint-import-resolver-typescript` to v4
and move the setting to `import-x/resolver-next` (`createTypeScriptImportResolver()`),
updating the peer dependency range, the lockfile, and the import rule documentation.

== Release and maintenance policy alignment

The root guide says newly enabled rules require a minor release while on `v0`.
The `prepare-release` skill distinguishes new error rules from automatically fixable warnings,
listing the latter as patch changes.
Resolve this wording before the next release; the root guide currently requires the stricter minor bump.

The `update-dependencies` skill explicitly places other development tooling before `@perfective/build`,
while the root guide and single-dependency skill omit that category from their ordering lists.
Align those lists when revising the maintenance workflow.
The manifest pins ESLint plugins but still uses ranges for several development tools;
clarify the scope of the root guide's exact-version requirement before changing those ranges.

== Automated PR review

The Codex review loop is removed, so no workflow reviews Renovate PRs or Claude issue PRs after Claude.

* Choose a second reviewer that runs on subscription pricing.
Cursor Bugbot and Cursor Automations bill outside the seat usage, so they do not qualify.
The Cursor CLI in GitHub Actions qualifies only if a test run with `CURSOR_API_KEY` uses the included usage.
Otherwise, use a review-only Claude job.
* Then add a fix loop for the findings (Claude fixes in rounds 1 and 2) and resolve the fixed threads.

== Agent guidance maintenance

Keep shared instructions in the root `AGENTS.md`, source details in `src/AGENTS.md`,
and task workflows in `.agents/skills/`.
`.claude/skills` is a symlink to the shared skills, so separate copies would drift.
When changing a workflow, update its matching guidance in the same commit.
Keep unapproved proposals in this file rather than presenting them as established policy.
